# 07-threat-model

```
상태: 확정(오케스트레이터)
브랜치: 07-threat-model (앞 브랜치: main @ efef733, 06-recon-analysis @ e8d2ecf를 머지한 끝)
문제: 1단계는 기계의 불확실성만 다뤘다. 운영자 계정이 탈취되거나, 내부자가 DB를 직접 고치거나,
      위험 판단기가 틀리거나 멈추거나, 의존성이 오염되면 I1–I6을 지키는 코드가 그대로 있어도
      "승인되지 않은 출금"과 "흔적 없는 기록 변경"이 가능하다. 무엇을 지키고 무엇을 믿지 않는지가
      문서로 정해져 있지 않아 08~10의 완료 기준을 쓸 수 없다.
지킬 불변조건: I7, I8, I9 (새로 정의). I1–I6은 고치지 않는다
```

설계 원본은 `ROADMAP.md`의 "2단계" 절, 1단계의 `docs/SYSTEM_INVARIANTS.md`·`FAILURE_SCENARIOS.md`·ADR 001–003, 현재 `vault::withdrawal`·`vault::signer`·마이그레이션이다. 00-charter처럼 코드가 없으므로 메인이 문서를 쓰고 평가 서브에이전트가 판정한다(ORCHESTRATION 2-1).

## 결정

- **위협 모델은 보호 대상 × STRIDE 표** / 대안: 공격 트리(목표별로 깊게 내려가지만 보호 대상이 5개뿐이라 표가 더 짧고 빠짐을 보기 쉽다) / 바꿀 신호: 위협 행이 25개를 넘거나 한 위협이 여러 단계 공격으로만 설명될 때.
  - 보호 대상 5개: 핫월렛 서명 키, 원장·출금 DB, 출금 경로(요청 → 승인 → 서명 → 전송), 체인 RPC, 빌드 공급망(crate·CI).
  - 행마다: 위협, STRIDE 분류, 막는 장치(있으면 기존 테스트 ID, 없으면 07~10의 새 테스트 ID), **남는 위험**(막지 않기로 한 것과 바꿀 신호).
- **신뢰 경계를 명시한다**: 믿는 것 = Postgres 소유자 역할을 가진 배포 절차, 서명 프로세스의 메모리. 믿지 않는 것 = 개별 운영자(승인자) 한 명, 앱 DB 역할, RPC 응답, 위험 판단기, 새 의존성 버전 / 대안: 운영자 전원 신뢰(1인 운영이면 단순하지만 계정 하나 탈취로 출금이 끝난다) / 바꿀 신호: 운영자가 1명뿐이라 다른 승인자가 없을 때 → 승인 수 정책을 금액 상한으로 대신한다.
- **I7–I9는 별도 절로 더한다** / 대안: I1의 "승인된"을 넓혀 다시 쓰기(AGENTS.md가 I1–I6 수정을 금지하고, 1단계 증명 테스트의 의미가 바뀐다) / 바꿀 신호: I7과 I1이 같은 상황에서 다른 결론을 낼 때 → 멈추고 사람에게 묻는다.
  - 공개 표기: "확정: 오케스트레이터".
- **ADR-004 출금 인가**: 승인은 원장과 같은 DB의 승인 기록(출금 ID, 승인자 ID, 시각)으로 남기고, 상태 기계에 승인 대기 상태를 둔다. 서명자는 서명 직전에 정책과 승인 기록을 *다시* 읽어 검증한다(처리기 검사가 우회되어도 서명 0건) / 대안: 처리기에서만 검사(한 곳이 뚫리면 끝), 서명 키 분할(MPC, 범위 밖) / 바꿀 신호: 서명이 다른 프로세스·기기로 옮겨질 때 → 승인을 서명된 증명으로 넘긴다.
  - 승인 API는 라이브러리 함수다(HTTP 없음). 승인자 인증은 범위 밖이고 `ApproverId`를 받은 것으로 가정한다고 위협 모델의 남는 위험에 적는다.
- **ADR-005 감사 기록·DB 권한**: (1) 새 마이그레이션에서 소유자 역할과 앱 역할을 나누고, 원장·출금 이벤트·승인 테이블에 앱 역할은 INSERT·SELECT만 갖는다. (2) 감사 로그는 행마다 `prev_hash`·`hash`(SHA-256, 직렬화 형식 고정)를 두는 해시 체인이고, 검증 함수가 끊긴 곳을 보고한다 / 대안: 외부 WORM 저장소(변조 방지까지 되지만 외부 의존), DB 트리거만(소유자가 트리거를 끄면 흔적 없음) / 바꿀 신호: 소유자 계정까지 위협에 넣어야 할 때.
  - 기존 마이그레이션은 고치지 않고 새 번호 파일로 더한다(AGENTS.md 금지 사항).
- **ADR-006 판단기 경계**: `RiskOracle` trait의 결과는 `Pass | Review(reason) | Indeterminate` 셋뿐이고, 처리기는 `Review`·`Indeterminate`를 검토 대기로만 보낸다. `Pass`도 I7 검사를 건너뛰게 하지 못한다. 판단기 프로세스의 DB 역할은 읽기 전용 뷰만 본다 / 대안: 점수로 승인 수를 줄이기(편하지만 모델이 틀리면 인가가 약해진다. I9 위반), 실패 시 열림(가용성은 좋지만 판단기를 멈추면 검사를 끌 수 있다) / 바꿀 신호: 없음. 판단기가 인가를 완화해야 한다는 요구는 I9를 뒤집는 발견이므로 멈추고 사람에게 묻는다.
- **장애 시나리오 F9–F12**: F9 운영자(승인자) 계정 하나 탈취, F10 앱 DB 계정으로 기록 직접 수정·삭제, F11 판단기 장애·오판·응답 위조, F12 의존성 오염(악성 crate 버전). 1단계 표처럼 시나리오마다 위협받는 불변조건과 테스트 ID를 단다.
- **테스트 표**: T7.x(08), T8.x(09), T9.x(10)를 1단계 표와 같은 열(`넣는 입력과 단언`, `실패해야 할 변형`, `변형을 가릴 수 있는 장치`)로 쓴다. 테스트 파일 `crates/vault/tests/invariants/i7_withdrawal_authz.rs`, `i8_audit.rs`, `i9_advisory_boundary.rs`에 `#[ignore = "08-withdrawal-authz"]` 같은 뼈대를 두고 `check-invariant-tests.sh`가 새 표를 읽도록 넓힌다.
  - 최소 후보: T7.1 승인 없는 출금 서명 0건, T7.2 요청자 자기 승인 거부, T7.3 같은 승인자 중복은 1명으로 셈, T7.4 한도·허용 목록 위반 거부, T7.5 처리기 검사를 건너뛰어도 서명자가 거부, T8.1 앱 역할 UPDATE·DELETE 거부, T8.2 소유자 변조 탐지, T8.3 키 문자열 비노출, T9.1 `Pass`도 I7을 건너뛰지 못함, T9.2 타임아웃·형식 오류는 검토로, T9.3 판단기 역할 쓰기 거부.

## 완료 기준

1. `docs/THREAT_MODEL.md`가 보호 대상 5개 각각에 STRIDE 6분류를 다 따졌고(해당 없음은 이유 한 줄), 위협 행마다 막는 장치의 테스트 ID 또는 남는 위험과 바꿀 신호가 있다
2. `docs/SYSTEM_INVARIANTS.md`에 I7–I9 절과 추적표가 있고, 불변조건마다 위협 → F9–F12 중 하나 이상 → 테스트 이름이 이어진다. I1–I6 절은 바뀌지 않았다(`git diff`로 확인)
3. 테스트 표의 모든 행에 `넣는 입력과 단언`, `실패해야 할 변형`, `변형을 가릴 수 있는 장치`가 있고, 평가가 행마다 "이 변형이 정말 테스트를 빨갛게 만드는가"를 판정한다
4. ADR-004·005·006마다 대안·결정·검증 방법·바꿀 신호가 있다
5. 테스트 뼈대가 ignore로 있고 `scripts/harness/verify.sh full`(check-invariant-tests 포함)과 `scripts/check-public.sh`가 통과한다
