# 00-charter

```
상태: 확정(오케스트레이터)
브랜치: 00-charter (앞 브랜치: main @ 6b4a912)
문제: 불변조건·장애 시나리오·결정이 문서로 고정되지 않으면, 뒤 브랜치의 구현과 테스트가 무엇을 증명해야 하는지 흔들린다.
      테스트가 "통과"해도 어떤 장애를 막는지 추적할 수 없다.
지킬 불변조건: I1–I6 (이 브랜치는 정의하고, 증명할 테스트 이름을 정한다)
```

## 결정

- 문서는 `docs/` 아래 7개로 둔다: REQUIREMENTS, SYSTEM_INVARIANTS, FAILURE_SCENARIOS, ARCHITECTURE, adr/001·002·003
  / 대안: 한 파일(DESIGN.md)에 모두 / 이유: ROADMAP과 README가 불변조건·시나리오·ADR을 행 단위로 링크해야 한다
  / 바꿀 신호: 문서 사이 중복이 3곳 넘게 생길 때 합친다
- 추적표의 원본은 SYSTEM_INVARIANTS 한 곳에만 둔다(불변조건 → 시나리오 → 테스트 이름 → 브랜치 → ADR). 다른 문서는 링크만 한다
  / 대안: 시나리오 문서에도 같은 표 / 이유: 두 곳에 두면 어긋난다 / 바꿀 신호: 없음(02 이후 테스트 경로가 생기면 이 표만 고친다)
- 테스트 이름은 지금 정하고 "예정 브랜치"를 단다. 각 테스트에 "이 변형에서 실패해야 한다"(깨뜨릴 구현)를 한 줄씩 단다
  / 대안: 테스트 이름을 각 브랜치에서 정함 / 이유: 평가 단계의 변형 검사가 이 줄을 기준으로 한다
  / 바꿀 신호: 구현 브랜치에서 테스트를 나누거나 합치면 그 브랜치에서 표를 고친다
- 금액은 정수 최소 단위(wei), Rust `u128`, DB `NUMERIC(78,0)`. 부동소수점 금지
  / 대안: i64 / 이유: wei는 i64를 넘는다 / 바꿀 신호: 없음
- 원장 계정 종류에 `network_fee`(비용)와 `operator_capital`(자본)을 더해 6개로 둔다. ROADMAP의 4개(사용자·잠정 입금·핫월렛·출금 대기)로는 가스비와 운영자가 출금 주소에 넣는 코인이 갈 곳이 없어 핫월렛 대사가 맞지 않는다
  / 대안: 가스비·운영 자금을 분개 없이 핫월렛 잔액에 반영 / 이유: I1·I3 위반 / 바꿀 신호: 사용자에게 출금 수수료를 받게 되면 수익 계정을 더한다
- 체인은 EVM 하나, 네이티브 코인만. ERC-20은 범위 밖
  / 이유: reorg·nonce·확정 문제는 네이티브 전송으로 모두 드러난다 / 바꿀 신호: 토큰 입금이 필요해질 때(log 기반 감지 추가)
- 프로세스는 단일 인스턴스, 단일 writer로 가정한다
  / 대안: 다중 인스턴스 + 리더 선출 / 이유: 정확성 증명이 목표이고 운영 부하가 없다 / 바꿀 신호: 가용성 요구가 생기면 Postgres advisory lock으로 단일 writer를 강제한다
- 개발 원칙 7개는 원문 기록이 없으므로 이 브랜치에 넣지 않는다. 사람에게 받으면 `docs/PRINCIPLES.md`로 더한다(출처: 사람 설계)

## 완료 기준

1. `docs/SYSTEM_INVARIANTS.md`에 I1–I6이 ROADMAP 문구 그대로 있고 "출처: 사람 설계" 표기가 있다
2. 추적표에서 모든 불변조건이 시나리오 1개 이상, 테스트 이름 1개 이상과 연결되고, 모든 시나리오(F1–F8)가 불변조건 1개 이상에 연결된다
3. 모든 테스트 이름에 예정 브랜치와 "실패해야 할 변형"이 있다
4. ADR 3개 모두 맥락·대안·결정·검증(어느 테스트)·바꿀 신호 절이 있다. ADR-002는 선택 B와 "출처: 사람 설계"
5. ARCHITECTURE의 결정마다 대안과 바꿀 신호가 있다
6. `scripts/check-public.sh docs/*.md docs/adr/*.md README.md` 통과(ai-work 브랜치의 스크립트로)

판정: 평가 서브에이전트가 1–5를 문서만 보고 판정한다. 6은 메인이 돌린다.
