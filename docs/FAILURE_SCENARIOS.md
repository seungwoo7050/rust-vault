# 장애 시나리오

시나리오 8개의 목록은 출처: 사람 설계. "어떻게 일어나나", "잘못 처리하면", "기대 동작" 열은 확정: 오케스트레이터.

각 시나리오를 어떤 테스트가 증명하는지는 [SYSTEM_INVARIANTS의 추적표](SYSTEM_INVARIANTS.md#추적표)에만 적는다. 이 문서는 장애의 모양과 기대 동작을 정한다.

| ID | 시나리오 | 어떻게 일어나나 | 잘못 처리하면 | 기대 동작 | 불변조건 |
| --- | --- | --- | --- | --- | --- |
| F1 | 블록 이벤트 중복 | 구독 재연결, 폴링 구간 겹침, 재시작 후 커서 직전 블록을 다시 읽음 | 같은 입금이 두 번 반영된다 | 입금 분개의 멱등 키(체인·tx 해시·블록 해시, [ADR-001](adr/001-ledger-model.md))로 두 번째 기록은 아무것도 바꾸지 않는다 | I2, I1 |
| F2 | reorg | 노드가 더 긴(무거운) 분기로 정본을 바꿈. 처리한 블록이 canonical에서 빠짐 | 사라진 tx의 입금이 남아 사용자가 없는 돈을 출금한다 | 새 블록의 부모 해시가 저장된 해시와 다르면 공통 조상까지 되감고, 확정 전 잠정 입금을 역분개한 뒤 새 분기를 처리한다. 확정 뒤 깊이의 reorg는 원장을 바꾸지 않고 사고로 기록하고 입금 처리를 멈춘다 | I4, I1, I3 |
| F3 | DB 커밋 직후 종료 | 원장 커밋은 됐지만 커서·출금 상태 갱신 전에, 또는 커밋 응답을 받기 전에 프로세스가 죽음 | 재시작 후 같은 블록을 다시 반영하거나, 반영한 블록을 건너뛴다 | 블록 하나의 원장 반영·블록 헤더 저장·커서 전진을 한 DB 트랜잭션으로 묶는다. 재시작하면 커서 다음 블록부터 다시 읽고, 다시 읽어도 멱등 키로 같은 상태가 된다 | I5, I2 |
| F4 | RPC 응답 유실 | (전송) `eth_sendRawTransaction` 요청은 노드에 닿았지만 응답이 타임아웃·연결 끊김으로 오지 않음. (조회) 블록·영수증 조회가 타임아웃되거나 빈 응답이 옴 | 실패로 보고 새로 서명해 다시 보내 이중 출금하거나, 홀드를 풀어 사용자가 다시 쓴다. 조회 실패 블록을 빈 블록으로 보고 넘어가 입금을 놓친다 | 결과를 모르는 오류는 `Unknown`으로 둔다. 실패로 판단하지 않고, 저장한 tx 해시로 영수증과 계정 nonce를 조회해서만 결론 낸다. 조회가 실패하면 커서를 움직이지 않고 다시 조회한다 | I6, I2, I1 |
| F5 | nonce 충돌 | 같은 핫월렛 nonce를 두 출금에 할당(동시 할당 버그)하거나, 외부에서 같은 키로 tx를 보냄 | 한 출금은 영원히 채굴되지 않는데 성공으로 보거나, 실패로 보고 다른 nonce로 다시 보내 이중 출금한다 | nonce는 DB에서 핫월렛 주소별로 한 트랜잭션 안에서 할당하고 서명 tx와 함께 저장한다. 계정 nonce가 내 nonce를 지났는데 내 tx 영수증이 없으면 홀드를 유지한 채 `NeedsReview`로 둔다(그 nonce를 쓴 tx가 같은 수취인에게 지급했을 수 있다, [ADR-003](adr/003-nonce-and-rpc-uncertainty.md)) | I6, I2, I1 |
| F6 | 출금 재전송 | 재시작 후, 또는 `Unknown`에서 같은 출금을 다시 보냄 | 새 서명(새 nonce·새 해시)으로 두 번째 tx가 나가 이중 출금된다 | 재전송은 저장한 raw tx 바이트를 그대로 보낸다. 같은 해시라 체인에서 최대 한 번만 들어간다. "already known"·"nonce too low" 응답은 실패가 아니라 조회 대상이다 | I2, I6 |
| F7 | DB 일시 장애 | 연결 끊김, 직렬화 실패, 커밋 타임아웃 | 원장 일부만 반영되거나, 커밋 성공 여부를 모르고 다시 반영한다 | 작업 단위 전체를 한 트랜잭션으로 두고 실패하면 통째로 다시 한다. 커밋 결과를 모르면 다시 해도 멱등 키 때문에 안전하다. DB 밖에 상태를 먼저 진전시키지 않는다(체인 전송은 서명 tx 커밋 뒤에만) | I5, I2, I3 |
| F8 | 이벤트 순서 변경 | 여러 블록이나 한 블록 안의 이벤트가 도착 순서와 다르게 들어옴(병렬 조회, 재시도) | 확정 판정이나 잔액이 처리 순서에 따라 달라진다 | 처리 순서는 도착 순서가 아니라 (블록 번호, tx 위치)로 정한다. 커서보다 앞선 블록은 받아도 기다리고, 같은 이벤트 집합이면 어떤 순서로 들어와도 최종 원장이 같다 | I4, I2 |

## 시나리오를 테스트로 만들 때

- 가짜 체인(`vault-sim`)이 F1·F2·F4·F5·F6·F8을 주입한다: 같은 블록 재전달, 분기 만들기·바꾸기, 응답 버리기(요청은 반영), nonce 선점, 이벤트 섞기.
- F3·F7은 장애 주입 지점(`store::FaultPoint`)으로 만든다: 이벤트 수신 직후(`BlockFetched`), 분개 기록 중간(`BlockEntriesWritten`: 분개는 썼고 커서 전진 전), 각 DB 커밋 직전(`BeforeCommit(Site)`), 각 DB 커밋 직후(`AfterCommit(Site)`: 커밋은 됐지만 호출자에게 오류를 돌려줌). `Site`는 `Block`(블록 처리), `Rewind`(되감기), `Withdrawal`(출금 상태 전이 하나)이다. 출금에는 전송 직후 지점(`AfterSend`: 전송 응답을 받고 상태를 쓰기 전)이 더 있다. 커밋 지점은 모든 커밋이 거치는 도우미 `store::commit`에 걸리므로, 구현이 트랜잭션을 나누면 나뉜 커밋 사이에도 자동으로 주입된다. 주입은 지점마다 `Faults::hit` 하나로 하고 종류는 종료(`Crash`), 일시 DB 오류(`Transient`), 커밋 결과 모름(`CommitOutcomeUnknown`)이다. 각 지점의 k번째 통과에서 종료한 뒤 재시작해 장애 없는 실행과 최종 원장을 비교하고(F3), 일시 오류는 재시작 없이 재시도해 비교한다(F7).
- 주입은 테스트 전용 설정으로만 켠다. 운영 코드 경로에 `if test` 분기를 두지 않고, 주입 지점은 trait 경계(체인 클라이언트, 저장소)에서 감싼다.
