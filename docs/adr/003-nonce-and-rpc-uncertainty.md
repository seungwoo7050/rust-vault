# ADR-003 출금의 nonce와 RPC 불확실성

상태: 확정: 오케스트레이터 · 지키는 불변조건: I6, I2, I1, I5

## 맥락

출금 tx를 보내는 RPC 호출은 세 가지로 끝난다: 받았다는 응답, 거절 응답, 그리고 아무 응답도 없음(타임아웃·연결 끊김). 마지막 경우 tx는 노드에 닿았을 수도 아닐 수도 있다. 이를 실패로 보고 새로 서명해 보내면 두 tx가 모두 채굴될 수 있다(이중 출금). 거꾸로 실패로 보고 홀드를 풀면 사용자가 그 돈을 다시 쓴다. EVM에서는 같은 주소의 tx가 nonce 순서로만 들어가고, nonce 하나에는 tx 하나만 들어간다. 이 성질이 이중 출금을 막는 도구다.

## 대안

| 문제 | 안 | 판단 |
| --- | --- | --- |
| 결과를 모를 때 | A. 타임아웃이면 실패 처리 | 이중 출금이나 홀드 해제. I6 위반 |
| | **B. `Unknown`에 두고 체인 조회로만 결론** | **고름** |
| | C. 결과가 나올 때까지 무한정 기다림 | 막힌 출금을 아무도 모른다. B에 "오래 걸리면 `NeedsReview`"를 더해 해결 |
| 재전송 | A. 재시도마다 다시 서명 | 서명마다 nonce·해시가 달라질 수 있어 이중 출금 |
| | **B. 서명한 raw tx를 저장하고 같은 바이트만 재전송** | **고름**. 같은 해시라 체인에 최대 한 번 들어간다 |
| nonce | A. 매번 노드의 pending nonce 조회 | 응답 유실·동시 출금 때 같은 nonce를 두 번 받는다 |
| | B. 메모리 카운터 | 재시작하면 잃는다 |
| | **C. DB에서 주소별로 할당하고 서명 tx와 같은 트랜잭션에 저장** | **고름** |

## 결정

1. **RPC 결과는 세 가지.** `Ok(값)`, `Definite(오류)`(노드가 판단해 돌려준 오류), `Indeterminate`(타임아웃, 연결 끊김, 5xx, 해석할 수 없는 응답). 체인 클라이언트 trait가 이 타입을 돌려주고, 호출자는 `Indeterminate`를 실패로 바꿀 수 없다(I6).
2. **상태 기계.**

   ```
   Held ──서명·nonce 할당(커밋)──▶ Signed ──전송──▶ Sent ─┐
                                        │                  ├─ 영수증, 확정 수 N, status 1 ──▶ Confirmed (wd:settle)
                                        └─ Indeterminate ─▶ Unknown ─┤
                                                                   ├─ 영수증, 확정 수 N, status 0 ──▶ Failed (wd:fee + wd:release)
                                                                   └─ 내 nonce를 다른 tx가 씀, 또는 기한 초과 ──▶ NeedsReview (홀드 유지)
                                                                                                        │
                                              조회 루틴은 NeedsReview에도 계속 돈다. 영수증이 나오면 ────┘ 위와 같이 Confirmed / Failed
   ```

   - `Held`: 요청 저장과 홀드 분개(`wd:hold:{request_id}`)를 한 트랜잭션에서. 잔액이 모자라면 요청은 `Rejected`이고 분개는 없다. 같은 `request_id`가 다시 오면 기존 요청을 돌려준다(I2).
   - `Signed`: 한 트랜잭션에서 nonce 할당 → 서명 → raw tx·tx 해시·nonce 저장. 커밋되지 않은 서명 tx는 절대 보내지 않는다. 커밋이 실패하면 서명 tx도 nonce도 없던 일이 된다(I5).
   - 전송 응답이 `Ok`이거나 `Definite`라도 "already known", "nonce too low", "replacement underpriced"면 `Sent`로 두고 조회로 넘긴다. 이 셋은 "이미 들어갔을 수 있음"이라는 뜻이라 실패가 아니다.
   - `Indeterminate`면 `Unknown`.
   - 그 밖의 `Definite` 오류(예: "insufficient funds", 노드의 일시 거절)도 `Unknown`이다. 이 노드가 지금 거절했다는 사실이 앞서 보낸 같은 tx가 다른 곳에 없다는 증거는 아니다. 전송 오류만으로 `Failed`가 되는 전이는 없다.
   - `Unknown`과 `Sent`는 같은 조회 루틴으로 결론 낸다. 조회 루틴의 재전송 응답이 `Ok`·"already known"이면 `Sent`, 그 밖이면 상태를 그대로 둔다(되돌아가는 전이 없음).
3. **결론은 체인 조회로만.** 저장한 tx 해시로 영수증을 조회한다.
   - 영수증이 있고 그 블록의 확정 수가 N 이상이면 status에 따라 `Confirmed`(지급 분개) 또는 `Failed`(가스비 분개 + 홀드 해제). 확정 수 계산은 [ADR-002](002-reorg-handling.md)와 같다.
   - 영수증이 있다가 reorg로 사라지면 `Sent`로 돌아가 같은 raw tx를 다시 보낸다.
   - 영수증이 없고 주소의 확정된 nonce가 내 nonce 이하면 아직 안 들어간 것이다. 같은 raw tx를 다시 보낸다.
   - 영수증이 없는데 확정된 nonce가 내 nonce를 지났으면 다른 tx가 그 nonce를 썼다(F5: 외부에서 같은 키 사용, 또는 할당 버그). 내 tx는 이제 들어갈 수 없지만, 그 다른 tx가 같은 수취인에게 지급했을 수도 있다. 자동으로 홀드를 풀지 않고 `NeedsReview`.
   - 정해진 기한(설정값) 안에 결론이 안 나면 `NeedsReview`. 홀드는 유지한다. 자동 `Failed`는 없다.
   - `NeedsReview`는 "사람이 봐야 한다"는 표시이지 결론이 아니다. 조회 루틴은 `NeedsReview`에서도 계속 돌고, 영수증이 확정 수 N에 이르면 위와 같이 `Confirmed`(지급 분개) 또는 `Failed`로 간다. 시간이 지났다는 이유만으로는 어떤 상태도 `Failed`가 되지 않는다(I6).
   - 기한은 `Clock` trait로 잰다. 테스트는 가짜 시계를 앞으로 돌려 기한 전후를 만든다.
4. **재전송은 같은 바이트만.** 재시작 루틴, `Unknown`, reorg 뒤 재전송 모두 저장된 raw tx를 그대로 보낸다. 다시 서명하는 코드 경로를 두지 않는다. 서명 함수는 `Held → Signed` 전이에서만 부른다.
5. **nonce 할당.** `wallet_nonces(address, next_nonce)` 행을 `SELECT … FOR UPDATE`로 잠그고 할당·증가한다. 처음 한 번만 체인의 확정 nonce로 초기화하고, 그 뒤로는 DB가 원본이다. 출금 주소의 키를 이 시스템 밖에서 쓰지 않는다는 것이 운영 전제다(어기면 3의 `NeedsReview`로 드러난다).
6. **확정 뒤 깊이의 reorg.** `Confirmed` 출금의 tx가 확정 수 N보다 깊은 reorg로 빠지면 입금과 같이 정책 가정이 깨진 것이다([ADR-002](002-reorg-handling.md) 결정 7). 원장은 바꾸지 않고(지급 분개를 되돌리지 않는다) `finality_violations`에 출금으로 기록하고 출금 처리를 멈춘다. 같은 raw tx가 새 분기에 다시 들어갈 수 있으므로 자동 재전송·재서명도 하지 않는다.
7. **재시작 루틴.** `Signed`는 다시 보내고, `Sent`·`Unknown`은 조회 루틴에 넣는다. 전송 직후 상태를 쓰기 전에 죽었으면 `Signed`로 남아 같은 바이트가 다시 나가고, 노드는 "already known"을 돌려준다(I5).

## 검증

[SYSTEM_INVARIANTS](../SYSTEM_INVARIANTS.md#증명-테스트)의 T1.3, T2.4, T5.3, T6.1–T6.4, T6.6(05-withdrawal). T6.2는 기한 전과 기한 뒤(`NeedsReview`를 거쳐) 모두 `Confirmed`로 끝나는지 본다. 가짜 체인이 "요청은 반영하고 응답만 버림", 조회 타임아웃, 외부 tx의 nonce 선점, 영수증이 생겼다 사라지는 reorg를 주입한다. T6.6은 이를 무작위로 섞어 출금 요청마다 체인 지급 수 ≤ 1인지 본다.

## 바꿀 신호

| 신호 | 바꿀 것 |
| --- | --- |
| 낮은 가스비로 tx가 오래 멈춰 뒤 nonce까지 밀린다 | 같은 nonce로 가스비만 올린 대체 tx. 같은 출금의 서명 tx를 여럿 저장하고, 그중 하나라도 채굴되면 그것으로 결론 낸다(어느 것이 들어가도 지급은 한 번) |
| `NeedsReview`가 nonce 공백으로 뒤 출금을 막는다 | 그 nonce로 자기 자신에게 0 전송하는 취소 tx를 사람 승인으로 보내는 절차 |
| 출금 주소가 여럿 필요해진다(처리량, 키 분리) | 주소별 nonce 행은 이미 분리돼 있다. 출금을 주소에 배정하는 규칙만 더한다 |
| 노드를 여러 개 쓴다 | 같은 raw tx를 모든 노드에 보내도 안전하다(같은 해시). 조회는 다수 노드가 동의한 결과만 쓴다 |
