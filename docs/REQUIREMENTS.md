# 요구사항

확정: 오케스트레이터. 범위를 줄인 결정(crate 2개, 성능 최적화·HTTP API 제외)은 출처: 사람 설계.

## 목표

거래소 입출금처럼 사용자 자산을 맡아 체인과 주고받는 시스템에서, 블록체인의 불확실성(이벤트 중복, reorg, RPC 응답 유실)과 프로세스·DB 장애가 있어도 자산의 이동과 기록이 항상 올바르게 처리되게 한다. 기능 수가 아니라 [불변조건](SYSTEM_INVARIANTS.md)과 그것을 증명하는 테스트가 결과물이다.

## 도메인 용어

| 용어 | 뜻 |
| --- | --- |
| 원장(ledger) | 모든 자산 이동을 복식부기 분개로 기록하는 추가 전용 저장소. 잔액은 분개 합으로만 계산한다 |
| 분개(journal entry) | 한 번의 회계 거래. 여러 줄(line)로 되어 있고 줄 금액의 합은 0이다 |
| 멱등 키 | 분개마다 붙는 유일한 키. 같은 키로 두 번 기록하면 두 번째는 아무것도 바꾸지 않는다 |
| 잠정 입금 | 체인에서 보였지만 아직 확정 수에 이르지 않은 입금. 사용자가 쓸 수 없다 |
| 확정 수(confirmations) | 입금이 들어간 블록부터 현재 canonical head까지의 블록 수(그 블록 포함) |
| canonical chain | 노드가 지금 정본으로 보는 체인. reorg가 나면 바뀐다 |
| 홀드 | 출금 요청 금액을 사용자 잔액에서 출금 대기 계정으로 옮겨 다시 쓰지 못하게 하는 분개 |
| `Unknown` | 출금 tx를 보냈지만 결과를 모르는 상태. 체인 조회로만 벗어난다 |

## 기능 요구사항

| ID | 요구사항 | 브랜치 |
| --- | --- | --- |
| R1 | 사용자 잔액·잠정 입금·출금 대기·핫월렛·가스비·운영 자본을 복식부기 원장으로 기록한다([ADR-001](adr/001-ledger-model.md)) | 02-ledger |
| R2 | 모든 원장 기록은 멱등 키를 갖고, 같은 키의 재기록은 상태를 바꾸지 않는다 | 02-ledger |
| R3 | 블록을 순서대로 읽어 사용자 입금 주소로 들어온 네이티브 코인 전송을 잠정 입금으로 기록한다 | 03-deposit-reorg |
| R4 | 확정 수가 정책값 N에 이르면 잠정 입금을 사용자 잔액으로 옮긴다 | 03-deposit-reorg |
| R5 | 블록 해시 연결로 reorg를 감지하고, 확정 전 입금은 역분개한다. 확정 뒤에는 원장을 바꾸지 않고 사고로 기록한다 | 03-deposit-reorg |
| R6 | 처리 커서와 원장 반영을 한 DB 트랜잭션으로 묶어, 어느 지점에서 죽어도 재시작 후 같은 상태가 된다 | 04-crash-recovery |
| R7 | 출금은 요청 → 홀드 → 서명 → 전송 → 확정/실패의 상태 기계로 처리하고, 결과를 모르면 `Unknown`에 둔다 | 05-withdrawal |
| R8 | 서명한 tx를 전송 전에 저장하고, 재전송은 저장된 같은 tx만 보낸다 | 05-withdrawal |
| R9 | 온체인 잔액·tx와 원장을 대사해 불일치를 리포트한다 | 06-recon-analysis |

## 비기능 요구사항

- 정확성이 처리량보다 앞선다. 성능 측정과 최적화는 하지 않는다(출처: 사람 설계).
- 금액은 정수 최소 단위(wei)로만 다룬다. Rust `u128`, Postgres `NUMERIC(78,0)`. 부동소수점을 쓰지 않는다.
- 저장소는 Postgres 하나. 원장, 처리 커서, 블록 헤더, 출금 상태가 모두 같은 DB에 있어 한 트랜잭션으로 묶을 수 있다.
- 체인 접근은 trait 뒤에 둔다. 테스트는 가짜 체인(`vault-sim`)으로 하고, 실제 노드(anvil)는 06에서 기능 플래그로만 쓴다.
- 단일 프로세스, 단일 writer로 가정한다([ARCHITECTURE](ARCHITECTURE.md#결정)).

## 범위 밖

| 뺀 것 | 이유 | 다시 넣을 신호 |
| --- | --- | --- |
| 성능 최적화, benches (출처: 사람 설계) | 정확성 증명이 목표이고 측정할 운영 부하가 없다 | 블록당 처리 시간이 블록 간격에 가까워질 때 |
| crate 5개 분리 (출처: 사람 설계) | 경계는 모듈로 충분하다 | 모듈 하나를 다른 프로세스로 띄워야 할 때 |
| HTTP API 서버 (출처: 사람 설계) | 불변조건 증명은 라이브러리와 테스트로 충분하다 | 외부에서 출금을 요청해야 할 때 |
| 멀티체인, UTXO 체인 | EVM 하나로 reorg·nonce·확정 문제를 모두 보인다 | 체인 trait 구현이 두 번째로 필요할 때 |
| ERC-20 토큰 | 네이티브 전송으로 같은 문제가 드러난다 | 토큰 입금이 필요할 때(log 기반 감지 추가) |
| HSM·MPC 서명 | 서명은 trait 뒤의 로컬 키로 대신한다 | 실제 자산을 다룰 때 |
| 입금 주소 → 출금 주소 sweep | 내부 이동일 뿐 출금과 같은 상태 기계로 처리되어 새 불변조건을 보이지 않는다 | 입금 주소에 쌓인 코인으로 출금해야 할 때([ADR-001](adr/001-ledger-model.md)) |
| 가스비 올려 재전송(replacement) | 같은 nonce의 tx가 여럿 생겨 05의 증명 범위가 넓어진다 | 낮은 가스비로 tx가 오래 멈추는 일이 실제로 생길 때([ADR-003](adr/003-nonce-and-rpc-uncertainty.md)) |
| 출금 수수료(사용자 부담) | 수익 계정이 늘 뿐 불변조건 증명과 무관하다 | 수수료 정책이 생길 때 |
